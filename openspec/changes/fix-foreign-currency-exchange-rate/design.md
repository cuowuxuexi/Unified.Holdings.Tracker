# 技术设计文档：外币交易汇率换算修复

## Context

### 背景

Unified Holdings Tracker 是一个多市场投资组合管理应用，支持 A股（CNY）、港股（HKD）、美股（USD）三个市场。系统的核心原则是**所有金额统一换算为人民币（CNY）进行存储和计算**，以便于资产汇总和收益分析。

### 当前问题

用户报告在执行以下操作时，汇率换算未生效：
1. **卖出港股/美股**：卖出100港元的股票，系统显示现金增加100元人民币（预期应为92元）
2. **收到港股/美股股息**：收到100港元股息，系统显示现金增加100元人民币

### 已有的修复尝试

用户已经：
1. 修改了 `storage.prisma.ts` 中的 BUY/SELL/DIVIDEND 分支，添加了汇率换算逻辑
2. 修改了 `portfolio.ts` 后端API，添加了币种自动推断
3. 重新编译了 `packages/infra` 包
4. 重启了后端服务

但问题仍然存在，这表明可能存在以下几种情况：
- 编译产物未被正确加载
- 汇率服务调用失败
- 前端数据传递不完整
- 代码逻辑执行路径有误

### 系统架构概览

```
Frontend (React)
    ↓ HTTP POST /api/portfolio/:id/transactions
Backend API Layer (Express)
    ↓ container.addTransactionUseCase.execute()
Use Case Layer (Domain Logic)
    ↓ storage.addTransactionToPortfolio()
Storage Layer (Prisma ORM)
    ↓ 汇率换算 + 数据保存
Database (SQLite)
```

## Goals / Non-Goals

### Goals

1. **确保汇率换算正确执行**：SELL 和 DIVIDEND 操作在所有场景下都能正确进行汇率换算
2. **完整保存汇率信息**：数据库中的交易记录包含 `currency` 和 `exchangeRate` 字段
3. **提供详细日志**：便于开发者调试和用户审计
4. **建立可靠的编译-部署流程**：确保代码修改后能正确生效
5. **汇率服务容错**：API失败时有备用方案

### Non-Goals

1. **不改变数据库 schema**：现有 schema 已经支持所需字段，无需迁移
2. **不重构整体架构**：仅修复汇率换算问题，不改变整体设计
3. **不支持更多币种**：暂时只支持 CNY、HKD、USD 三种币种
4. **不修复历史数据**：重点解决新交易，历史数据修复作为可选任务

## Decisions

### Decision 1: 诊断优先策略

**决策**：在修复代码前，先进行全面的诊断，确定问题的真正根因。

**理由**：
- 用户已经做了修复但问题仍存在，说明可能不是代码逻辑问题
- 可能是环境、编译、部署、数据传递等问题
- 盲目修改代码可能徒劳无功

**实施方式**：
1. 在开发环境重现问题
2. 检查编译产物和文件时间戳
3. 查看前端请求体内容
4. 验证汇率服务是否正常
5. 在关键位置添加日志追踪执行路径

### Decision 2: 增强日志而非移除日志

**决策**：保留并增强汇率换算相关的日志输出，而不是为了"清洁"而移除它们。

**理由**：
- 汇率换算是关键业务逻辑，涉及资金计算，必须有审计追踪
- 详细日志有助于快速定位问题
- 日志对性能影响极小，不是性能瓶颈

**实施方式**：
- 在 SELL/DIVIDEND 分支输出原始金额、汇率、换算后金额
- 在币种推断时输出推断结果
- 在数据库保存前输出最终数据

### Decision 3: 编译产物验证机制

**决策**：建立自动化脚本，确保 infra 包修改后能正确编译并加载。

**理由**：
- 用户报告多次重新编译和重启，但问题仍存在，说明可能存在编译或加载问题
- TypeScript 项目的编译产物和源码不同步是常见问题
- 手动操作容易出错或遗漏步骤

**实施方式**：
- 创建 `scripts/rebuild-infra.sh` 或 `.ps1` 脚本
- 脚本执行：`cd packages/infra && npm run build && cd ../../apps/backend && pkill node && npm run dev`
- 或使用 `concurrently` 和 `nodemon` 实现自动化 watch

**替代方案考虑**：
- **方案A**：使用 `ts-node` 直接运行 TypeScript 源码
  - 优点：无需编译
  - 缺点：启动速度慢，生产环境不适用
  - **结论**：不采用，保持现有编译方式
- **方案B**：使用 monorepo 工具（如 Lerna、Turborepo）管理依赖
  - 优点：自动管理包依赖和编译顺序
  - 缺点：引入新工具，学习成本高
  - **结论**：暂不采用，当前项目规模不需要

### Decision 4: 汇率服务三级容错机制

**决策**：汇率服务在获取汇率时采用三级容错：API → 缓存 → 默认值。

**理由**：
- 外部汇率API可能不稳定
- 汇率短期内变化不大，使用缓存或默认值不会造成严重误差
- 不应因汇率获取失败而拒绝用户交易

**实施方式**：
1. **第一级**：尝试调用外部汇率API（如腾讯财经）
2. **第二级**：如果API失败，使用缓存的汇率（24小时内有效）
3. **第三级**：如果缓存也没有，使用预设的默认汇率（HKD: 0.92, USD: 7.2）

**默认汇率设定**：
```typescript
const FALLBACK_RATES: Record<string, number> = {
  'HKD': 0.92,  // 港币对人民币，基于近期汇率
  'USD': 7.25,  // 美元对人民币，基于近期汇率
  'CNY': 1.0,   // 人民币
};
```

**风险和缓解**：
- 风险：默认汇率可能与实际汇率有偏差
- 缓解：记录警告日志，提醒开发者检查汇率API；定期更新默认汇率值

### Decision 5: 币种自动推断逻辑

**决策**：后端根据资产代码前缀自动推断币种，前端可选传递 `currency` 字段。

**理由**：
- 前端可能不了解币种规则，由后端统一处理更可靠
- 资产代码前缀（sh/sz/hk/us）已经包含了市场信息，可以直接推断币种
- 但允许前端传递 `currency`，以支持未来可能的自定义需求

**推断规则**：
```typescript
function inferCurrency(assetCode: string): string {
  const lowerCode = assetCode.toLowerCase();
  if (lowerCode.startsWith('hk')) return 'HKD';
  if (lowerCode.startsWith('us')) return 'USD';
  if (lowerCode.startsWith('sh') || lowerCode.startsWith('sz')) return 'CNY';
  return 'CNY'; // 默认
}
```

**执行位置**：
- 在 `apps/backend/src/routes/portfolio.ts` 的 POST 请求处理中
- 在验证完成后、调用 Use Case 之前

### Decision 6: 不修改前端表单（暂时）

**决策**：暂时不修改前端表单以传递 `currency` 字段，依赖后端自动推断。

**理由**：
- 后端推断逻辑已经足够可靠
- 修改前端增加了变更范围和测试成本
- 如果后端推断有效，前端修改不是必需的

**未来考虑**：
- 如果需要支持同一资产代码多币种（如港股同时在A股上市）
- 如果需要支持更多市场（如新加坡、日本）
- 那时可以在前端添加币种选择器

## Risks / Trade-offs

### Risk 1: 默认汇率可能过时

**风险**：当汇率API长期失败时，使用的默认汇率可能与实际汇率有较大偏差。

**影响**：用户的资产计算不准确，但不会影响实际持仓（持仓基于数量，不基于金额）。

**缓解措施**：
- 记录明显的警告日志，提醒开发者
- 定期（如每月）检查并更新默认汇率值
- 在后续版本中，当使用默认汇率时，在UI中显示警告标识

**接受度**：可接受。这是一个在可靠性和准确性之间的权衡，我们优先保证系统可用性。

### Risk 2: 历史数据的汇率字段缺失

**风险**：已有的交易记录可能没有 `currency` 和 `exchangeRate` 字段，导致历史数据不完整。

**影响**：
- 用户无法追溯历史交易的原始币种
- 如果需要重新计算历史收益，可能缺少必要信息

**缓解措施**：
- 查询时提供默认值（currency: 'CNY', exchangeRate: 1.0）
- 创建可选的数据修复脚本（见 tasks.md 第7节）
- 在UI中显示时，对缺失字段的交易添加标注

**接受度**：可接受。修复历史数据不是紧急任务，可以作为后续优化。

### Trade-off: 日志详细度 vs 日志噪音

**权衡**：详细的日志有助于调试，但可能造成日志噪音。

**决策**：在汇率换算这个关键环节，选择详细日志。

**理由**：
- 汇率换算涉及资金计算，属于高风险操作
- 交易频率不高（不像查询操作），日志量可控
- 可以通过日志级别（如 `logger.debug`）在生产环境降低输出

**实施**：
- 开发和测试环境：输出详细日志
- 生产环境（未来）：可以通过环境变量控制日志级别

### Trade-off: 编译步骤 vs 开发体验

**权衡**：TypeScript 编译增加了开发步骤，但提供了类型安全。

**决策**：保持当前的编译方式，但通过自动化脚本改善体验。

**理由**：
- TypeScript 是项目既定的技术栈，类型安全对于财务应用很重要
- 编译步骤不可避免，但可以通过工具自动化
- 相比重构为 ts-node 或引入新工具，当前方案成本最低

## Migration Plan

### 第1步：诊断和日志增强（不影响现有功能）

- 添加日志到关键位置
- 不改变任何业务逻辑
- 在开发环境测试，观察日志输出
- **回滚方案**：移除添加的日志代码

### 第2步：验证和修复存储层逻辑（低风险）

- 根据诊断结果，修复存储层的汇率换算逻辑（如有必要）
- 确保编译和部署流程正确
- 使用测试投资组合验证修复
- **回滚方案**：恢复到上一个提交的代码版本

### 第3步：完善汇率服务容错（增强可靠性）

- 添加三级容错机制
- 设置默认汇率
- 添加汇率合理性验证
- **回滚方案**：移除容错逻辑，保留原有的直接API调用

### 第4步：全面测试（确保质量）

- 单元测试、集成测试、手动测试
- 在开发环境验证各种场景
- **回滚方案**：如果测试失败，不发布到生产

### 第5步：可选的历史数据修复（后期优化）

- 创建数据修复脚本
- 在非生产时间执行
- 备份数据库后再修复
- **回滚方案**：从备份恢复数据库

### 部署策略

- **开发环境**：立即部署，观察几天
- **生产环境**（如适用）：在下一个版本发布窗口部署
- **监控指标**：
  - 观察 `currency` 和 `exchangeRate` 字段是否正确保存
  - 观察汇率API调用成功率
  - 观察用户报告的现金余额是否准确

## Open Questions

### Q1: 是否需要在 UI 中显示原始币种和汇率？

**现状**：当前UI可能只显示换算后的人民币金额。

**问题**：用户是否需要看到"原价100港元，按汇率0.92换算为92元人民币"这样的信息？

**影响**：如果需要，要修改前端显示逻辑。

**建议行动**：在修复后端逻辑后，征求用户反馈，再决定是否修改前端显示。

### Q2: 汇率获取的时机是交易发生时还是查询时？

**现状**：交易发生时获取汇率并保存。

**问题**：是否需要支持"重新计算"功能，允许用户用最新汇率重新计算历史交易？

**影响**：如果需要，要添加"刷新汇率"功能。

**建议行动**：暂时不支持，交易汇率应是交易发生时的汇率（历史快照）。

### Q3: 汇率精度是多少位小数？

**现状**：Prisma Decimal 类型，默认精度较高。

**问题**：汇率应该保留几位小数？四位（0.9189）还是两位（0.92）？

**影响**：影响计算精度和显示。

**建议行动**：在数据库中保留高精度（如4位），在UI显示时可以根据需要格式化。

### Q4: 是否需要支持手动输入汇率？

**现状**：汇率完全由系统自动获取。

**问题**：是否允许用户在某些情况下手动输入汇率（如API失败时，或用户知道准确汇率）？

**影响**：需要修改前端表单和后端验证。

**建议行动**：暂时不支持，保持系统简单；如果用户强烈需求，可以在后续版本添加。

## Summary

本次修复的核心是**诊断优先、日志驱动、容错保障**。我们不急于修改代码，而是先全面诊断问题根因，然后通过增强日志和容错机制，确保汇率换算在所有场景下都能正确执行。同时，我们建立自动化的编译部署流程，避免代码修改后不生效的问题。

关键技术点：
1. 存储层的汇率换算逻辑必须正确执行
2. 币种信息由后端根据资产代码自动推断
3. 汇率服务采用三级容错：API → 缓存 → 默认值
4. 详细的日志记录便于调试和审计
5. 自动化编译部署脚本确保代码生效

风险可控，主要是默认汇率可能过时和历史数据不完整，这些都有相应的缓解措施。
