# 前后端一体化架构方案 (The "Radical" Approach)

> **状态**：建议
> **日期**：2025-11-18
> **核心理念**：移除 HTTP 网络层，使用 IPC 直接通信，将后端作为 Electron 的一部分运行。

## 🚀 核心差异

| 特性         | 传统方案 (Current)                  | 一体化方案 (Integrated)                           |
| ------------ | ----------------------------------- | ------------------------------------------------- |
| **运行模式** | 独立进程 (Electron + Node.exe)      | **单进程** (Electron Main) 或 **Utility Process** |
| **通信方式** | HTTP (TCP/IP Loopback)              | **IPC** (内存直连)                                |
| **端口占用** | 需要开放 `3001`                     | **无端口** (Zero Ports)                           |
| **安全性**   | 端口可能被外部扫描                  | **完全隔离**                                      |
| **前端调用** | `axios.get('http://localhost:...')` | `window.api.request(...)`                         |

## 🛠️ 架构设计

### 1. 移除 HTTP 监听

不再调用 `app.listen(3001)`。
后端代码仅导出 `Express Application` 实例。

```typescript
// apps/backend/src/server.ts
export const createApp = () => {
  const app = express();
  // ... 配置路由 ...
  return app;
};
// 不再自动启动 listen
```

### 2. IPC 适配层 (The Bridge)

在 Electron 主进程中，创建一个“虚拟网络适配器”。当接收到前端的 IPC 请求时，伪造 `Request` 和 `Response` 对象传给 Express App。

**技术实现**：
使用 `supertest` 的底层库或自定义适配器。

```typescript
// electron/src/bridge.ts
import { createApp } from '../../apps/backend/src/server';
const backendApp = createApp();

ipcMain.handle('api-request', async (event, options) => {
  // options: { method, url, body, headers }

  // 模拟请求进入 Express
  // 这里可以使用 supertest 的 agent，或者简单的 mock
  const response = await processRequest(backendApp, options);

  return response; // { status, data, headers }
});
```

### 3. 前端改造 (The Adapter)

前端不再直接发送 HTTP 请求，而是通过 Axios Adapter 拦截所有请求并走 IPC 通道。

```typescript
// frontend/src/api/axios-adapter.ts
import axios from 'axios';

axios.defaults.adapter = async (config) => {
  // 开发环境 (Web): 走默认 XHR
  if (!window.electron) {
    return axios.defaults.adapter!(config);
  }

  // 生产环境 (Electron): 走 IPC
  const response = await window.electron.api.request({
    method: config.method,
    url: config.url,
    data: config.data,
    headers: config.headers,
  });

  return {
    data: response.data,
    status: response.status,
    statusText: 'OK',
    headers: response.headers,
    config,
    request: {},
  };
};
```

## 🚧 实施挑战与解决

### 挑战 1：Prisma 二进制文件

**问题**：Prisma 依赖 Query Engine (.exe/.node)，打包在 asar 中可能无法执行。
**解决**：

1. 使用 `esbuild` 打包后端 JS。
2. 配置 `electron-forge` 将 Prisma Engine 复制到 `resources` 目录。
3. 运行时通过 `process.env.PRISMA_QUERY_ENGINE_BINARY` 指向解压后的路径。

### 挑战 2：性能阻塞

**问题**：如果在 Electron 主进程直接运行繁重的后端计算（如 PnL 递归计算），会卡死 UI。
**解决**：
**使用 Electron Utility Process** (推荐)。
这是一个专用的 Node.js 进程，由 Electron 管理，支持 IPC，但不会阻塞主线程 UI。

## 📅 激进版实施路线

1.  **Backend**: 使用 `esbuild` 打包为 `backend-bundle.js` (CommonJS)。
2.  **Electron**: 创建 `electron/src/backend-worker.ts` (Utility Process)。
    - 在此 Worker 中导入 `backend-bundle.js`。
    - 建立 `ipcMain` <-> `UtilityProcess` <-> `Express` 的通信链路。
3.  **Frontend**: 注入 Axios IPC Adapter。

## ⚖️ 决策建议

- **如果您追求极致体验**（启动快、无黑窗、无防火墙弹窗）：选择**一体化方案**。
- **如果您追求稳定性**（改动最小）：选择**Electron 托管方案**（上一个方案）。

鉴于您询问了“更激进”的方案，**一体化方案**是 Electron 应用的终极形态。
