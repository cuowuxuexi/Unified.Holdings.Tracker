# 打包架构优化方案

> **状态**：草稿
> **日期**：2025-11-18
> **目标**：修复当前不可用的打包应用，并优化体积和架构

## 🚨 核心问题发现

经过对现有代码（`electron/main.ts`）的分析，发现当前打包方案存在**致命缺陷**：

**Electron 主进程并未启动后端服务。**

代码仅检查了 `localhost:3001` 是否通畅（`checkBackendService`），假设后端已经运行。这在开发模式（`npm run dev`）下有效，但在打包后的独立应用中，后端服务不会自动启动，导致用户打开应用后只能看到"后端服务未运行"的报错。

## 💡 推荐方案：Electron 托管式后端架构

为了解决上述问题并提供“更好”的打包体验，我建议实施以下架构变更：

### 1. 架构变更

从“独立服务架构”转变为“Electron 托管架构”：

- **当前**：Electron 和 后端是两个独立的进程，没有父子关系。
- **新方案**：Electron 主进程作为父进程，负责 `spawn` (孵化) 或 `fork` (分叉) 后端 Node.js 进程，并管理其生命周期（启动、停止、重启）。

### 2. 构建流程优化（引入 esbuild）

目前后端构建仅使用 `tsc`，导致 `node_modules` 极其庞大且文件碎片化严重。

**建议**：
使用 `esbuild` 将后端代码打包为**单个 JS 文件**（Bundle）。

- **优势**：
  - **体积骤减**：通过 Tree-shaking 移除未使用的代码，不再需要携带完整的 `node_modules`。
  - **启动极快**：单文件加载比读取数千个小文件快得多。
  - **源码保护**：混淆和压缩代码。
  - **路径清晰**：只有一个入口文件，方便 Electron 调用。

### 3. Prisma 与 Native 模块处理策略

Prisma 是打包的难点，因为它包含二进制引擎文件。

**建议策略**：

1. **Bundle 排除**：将 `@prisma/client` 设为 `external`（不打包进 bundle.js）。
2. **自动复制**：在打包脚本中，将生成的 Prisma Client 和 Query Engine 复制到 Electron 的 `resources` 目录。
3. **动态路径**：在 Electron 启动后端时，注入环境变量，告知 Prisma Engine 的确切位置。

## 📝 实施路线图

### 第一步：引入 esbuild

安装 `esbuild` 并创建后端打包脚本。

```bash
npm install --save-dev esbuild
```

创建 `apps/backend/build.js`：

```javascript
// 伪代码
require('esbuild').build({
  entryPoints: ['src/server.ts'],
  bundle: true,
  platform: 'node',
  outfile: 'dist/server-bundle.js',
  external: ['electron', '@prisma/client'], // 排除 native 模块
  // ...
});
```

### 第二步：改造 Electron 主进程

修改 `electron/main.ts`，添加启动后端的逻辑：

```typescript
// 伪代码
import { fork } from 'child_process';

function startBackend() {
  const backendPath = app.isPackaged
    ? path.join(process.resourcesPath, 'backend/server-bundle.js')
    : path.join(__dirname, '../../apps/backend/dist/server.js');

  const backendProcess = fork(backendPath, [], {
    env: { ...process.env, DATABASE_URL: ... }
  });

  // 监听后端输出，等待 'Server is running' 信号
}
```

### 第三步：配置资源复制

修改 `forge.config.js` 或添加 `afterBuild` 钩子，将后端 bundle 和 Prisma 依赖复制到打包产物中。

### 第四步：验证与清理

- 确保应用退出时杀死后端子进程。
- 验证数据库文件的读写权限（userData 目录）。

## 📊 方案对比

| 特性           | 当前方案                       | 推荐方案 (Better)     |
| -------------- | ------------------------------ | --------------------- |
| **可用性**     | ❌ **不可用** (需手动启动后端) | ✅ **开箱即用**       |
| **启动方式**   | 被动检查端口                   | 主动管理进程          |
| **构建产物**   | 散乱的文件 + 完整 node_modules | 单个 server-bundle.js |
| **安装包体积** | 巨大 (>300MB 预估)             | 优化 (<150MB 预估)    |
| **启动速度**   | 慢 (大量 I/O)                  | 快                    |
