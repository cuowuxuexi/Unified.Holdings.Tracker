## 🔍 根本原因分析

### Git 的职责范围

Git 是**源代码版本控制系统**，它只管理被跟踪的文件。以下内容**不在 Git 管理范围内**：

| 类别 | Git 是否管理 | 原因 | 影响 |
|------|-------------|------|------|
| 源代码（.ts, .tsx） | ✅ 管理 | 这是 Git 的核心职责 | 回退后会恢复到旧版本 |
| 配置模板（.env.example） | ✅ 管理 | 提供配置参考 | 回退后会恢复 |
| Schema 定义（schema.prisma） | ✅ 管理 | 定义数据库结构 | 回退后会恢复到旧版本 |
| node_modules/ | ❌ 不管理 | .gitignore 忽略 | 回退后**不会变化** |
| dist/, build/ | ❌ 不管理 | .gitignore 忽略 | 回退后**不会变化** |
| .env 文件 | ❌ 不管理 | .gitignore 忽略 | 回退后**不会变化** |
| *.db 数据库文件 | ❌ 不管理 | .gitignore 忽略 | 回退后**不会变化** |
| .prisma/ 生成代码 | ❌ 不管理 | .gitignore 忽略 | 回退后**不会变化** |

### 问题产生的根源

假设你的工作流程：

**第 1 天（Commit A）**：
```bash
# schema.prisma 版本 1.0
model Portfolio {
  id   Int    @id @default(autoincrement())
  name String
}

# 运行
npm install          # 安装依赖版本 A
npm run db:push      # 数据库结构 = v1.0
npm run build        # 编译产物 = v1.0
git commit -m "v1.0"
```

**第 2-5 天（多次修改）**：
```bash
# schema.prisma 版本 2.0
model Portfolio {
  id          Int    @id @default(autoincrement())
  name        String
  description String  # 新增字段
  createdAt   DateTime @default(now())  # 新增字段
}

# 运行
npm install          # 安装依赖版本 B（可能更新了）
npm run db:push      # 数据库结构 = v2.0
npm run build        # 编译产物 = v2.0
git commit -m "v2.0"
```

**第 6 天（回退到 Commit A）**：
```bash
git reset --hard <Commit A>
```

**此时的状态**：

| 组件 | 期望版本 | 实际版本 | 结果 |
|------|---------|---------|------|
| schema.prisma | v1.0 ✅ | v1.0 | Git 恢复了 |
| 数据库结构 | v1.0 ❌ | v2.0 | **不匹配！** |
| node_modules | v1.0 ❌ | v2.0 | **不匹配！** |
| Prisma Client | v1.0 ❌ | v2.0 | **不匹配！** |
| 编译产物 | v1.0 ❌ | v2.0 | **不匹配！** |

### 具体错误场景

#### 场景 1：Schema 与数据库不匹配

```typescript
// schema.prisma (v1.0 - 回退后)
model Portfolio {
  id   Int    @id
  name String
}

// 数据库 portfolio.db (v2.0 - 未回退)
// 表结构：id, name, description, createdAt

// Prisma Client 运行时
const portfolios = await prisma.portfolio.findMany();
// ❌ 错误：Prisma Client 期望有 description 字段（因为用的是旧的生成代码）
// ❌ 但 schema.prisma 中没有定义这个字段
```

#### 场景 2：代码与依赖不匹配

```typescript
// 旧代码 (v1.0)
import { oldApi } from 'some-package';

// node_modules (v2.0)
// some-package 已经升级，oldApi 被重命名为 newApi

// 运行时
// ❌ 错误：Module 'some-package' has no exported member 'oldApi'
```

#### 场景 3：前端构建产物与源码不匹配

```typescript
// 源码 (v1.0 - 回退后)
function calculateTotal(items: Item[]): number { ... }

// dist/main.js (v2.0 - 未回退)
// 编译后的代码调用了新版本的 API
function calculateTotal(items, options) { ... }  // 新增了 options 参数

// Electron 启动时加载 dist/main.js
// ❌ 错误：参数不匹配，运行时崩溃
```

## 📝 详细修复步骤

如果自动化脚本失败或你想手动操作，按以下步骤执行：

### 步骤 1：停止所有进程

确保没有任何进程占用文件，否则清理会失败。

#### Windows

```batch
:: 停止所有 Node.js 进程
taskkill /f /im node.exe

:: 停止 Electron
taskkill /f /im electron.exe
```

#### Linux / macOS

```bash
# 停止所有 Node.js 进程
pkill -9 node

# 或者只停止项目相关进程
ps aux | grep "node.*backend" | awk '{print $2}' | xargs kill -9
```

### 步骤 2：清理不一致的环境

删除所有可能不一致的生成文件和缓存。

```bash
# 回到项目根目录
cd D:\optimize-branch-copy

# 清理 Prisma Client（重要！）
rm -rf node_modules/.prisma
rm -rf apps/backend/node_modules/.prisma

# 清理构建产物
rm -rf apps/backend/dist
rm -rf frontend/dist
rm -rf electron/renderer
rm -rf electron/main

# 清理 TypeScript 编译缓存
rm -rf **/*.tsbuildinfo

# （可选）如果依赖版本变化很大，完全重装
rm -rf node_modules
rm -rf apps/backend/node_modules
rm -rf frontend/node_modules
rm -rf electron/node_modules
```

### 步骤 3：重新安装依赖

确保依赖版本与 package.json 一致。

```bash
# 使用 workspace 模式安装所有依赖
npm install

# 如果出现依赖冲突
npm install --force

# 或者逐个模块安装
npm install -w backend
npm install -w frontend
```

### 步骤 4：重新生成 Prisma Client

根据当前的 schema.prisma 重新生成客户端代码。

```bash
# 生成 Prisma Client
npm run prisma:generate -w backend

# 如果遇到权限错误（Windows）
# 先手动删除临时文件
cd apps\backend\node_modules\.prisma\client
del query_engine-windows.dll.node.tmp*
cd ..\..\..\..

# 再重新生成
npm run prisma:generate -w backend
```

### 步骤 5：同步数据库结构

让数据库结构与当前的 schema.prisma 匹配。

#### 方式 1：使用 db:push（开发环境，快速）

```bash
npm run db:push -w backend
```

**优点**：快速，直接修改数据库
**缺点**：没有迁移历史，可能丢失数据

#### 方式 2：使用 migrate（推荐，生产环境）

```bash
# 创建迁移（如果还没有）
cd apps/backend
npx prisma migrate dev --name sync_after_reset

# 应用迁移（生产环境）
npx prisma migrate deploy
```

**优点**：有迁移历史，可回滚，安全
**缺点**：需要先设置 migrations

### 步骤 6：恢复配置文件

确保所有必需的 .env 文件存在。

```bash
# 检查并创建后端环境变量
if [ ! -f "apps/backend/.env" ]; then
  cp apps/backend/.env.example apps/backend/.env
  echo "⚠️ 请检查 apps/backend/.env 中的配置"
fi

# 检查并创建前端环境变量
if [ ! -f "frontend/.env" ]; then
  cp frontend/.env.example frontend/.env
  echo "⚠️ 请检查 frontend/.env 中的配置"
fi
```

### 步骤 7：重新构建项目

编译所有模块到最新状态。

```bash
# 构建后端
npm run build -w backend

# 构建前端
npm run build -w frontend

# 构建 Electron 主进程
npm run build:electron
```

### 步骤 8：验证恢复结果

启动项目并测试关键功能。

```bash
# 启动后端（新终端）
npm run dev:backend

# 启动前端（新终端）
npm run dev:frontend

# 或者一键启动（如果有配置）
npm run dev
```

**验证清单**：
- [ ] 后端成功启动，无数据库错误
- [ ] 前端成功启动，能访问 http://localhost:5173
- [ ] 前端能成功调用后端 API
- [ ] 数据能正常查询和保存
- [ ] Electron 应用能正常启动（如果适用）

## 🔧 常见错误排查

### 错误 1：`ENOENT: no such file or directory, open '...portfolio.db'`

**原因**：数据库文件路径配置不正确或文件不存在。

**解决方法**：

```bash
# 1. 检查配置文件中的路径
cat apps/backend/.env | grep DATABASE_URL
# 应该是：DATABASE_URL="file:./prisma/data/portfolio.db"

# 2. 检查文件是否存在
ls apps/backend/prisma/data/portfolio.db

# 3. 如果不存在，创建目录并初始化数据库
mkdir -p apps/backend/prisma/data
npm run db:push -w backend
```

**预防措施**：
- 使用相对于 backend 目录的路径
- 确保 data 目录在 Git 中（但 .db 文件被忽略）

### 错误 2：`@prisma/client did not initialize yet`

**原因**：Prisma Client 未生成或损坏。

**解决方法**：

```bash
# 1. 删除旧的 Prisma Client
rm -rf node_modules/.prisma
rm -rf apps/backend/node_modules/.prisma

# 2. 重新生成
npm run prisma:generate -w backend

# 3. 如果还是失败，完全重装依赖
rm -rf node_modules
npm install
npm run prisma:generate -w backend
```

### 错误 3：`EPERM: operation not permitted`（Windows）

**原因**：临时文件被其他进程锁定。

**解决方法**：

```batch
:: 1. 停止所有 Node 和 Electron 进程
taskkill /f /im node.exe
taskkill /f /im electron.exe

:: 2. 手动删除临时文件
cd apps\backend\node_modules\.prisma\client
del /f /q query_engine-windows.dll.node.tmp*

:: 3. 重新生成
cd ..\..\..\..
npm run prisma:generate -w backend
```

### 错误 4：`The table 'main.XYZ' does not exist`

**原因**：数据库结构与 schema.prisma 不匹配。

**解决方法**：

```bash
# 方法 1：强制同步（开发环境）
npm run db:push -w backend

# 方法 2：重置数据库（会丢失数据！）
cd apps/backend
npx prisma migrate reset

# 方法 3：手动创建迁移
npx prisma migrate dev --create-only
# 编辑生成的 SQL 文件，然后应用
npx prisma migrate deploy
```

### 错误 5：前端 `connect ECONNREFUSED 127.0.0.1:3001`

**原因**：后端未启动或端口配置不对。

**解决方法**：

```bash
# 1. 检查后端是否运行
curl http://localhost:3001/api/health
# 或
netstat -ano | findstr 3001  # Windows
lsof -i :3001                 # Linux/Mac

# 2. 检查前端配置
cat frontend/.env | grep VITE_API_BASE_URL
# 应该是：VITE_API_BASE_URL=http://localhost:3001/api

# 3. 重启后端
npm run dev:backend
```

### 错误 6：`Cannot find module '@some-package'`

**原因**：依赖版本不匹配或未安装。

**解决方法**：

```bash
# 1. 清理 node_modules
rm -rf node_modules
rm package-lock.json  # 如果需要

# 2. 重新安装
npm install

# 3. 如果是 workspace 问题
npm install -w backend
npm install -w frontend
```

## 🛡️ 预防措施

### 1. 使用 Prisma Migrations 代替 db:push

**为什么**：
- `db:push` 没有迁移历史，Git 回退后无法追溯数据库变化
- `migrate` 会生成 SQL 文件，Git 可以跟踪，回退后可以重放

**操作**：

```bash
# 创建迁移而不是 push
npx prisma migrate dev --name add_description_field

# Git 会记录 prisma/migrations/ 目录中的 SQL 文件
git add apps/backend/prisma/migrations
git commit -m "feat: add description field to Portfolio"
```

**更新 .gitignore**：

```gitignore
# 允许提交 migrations
# prisma/migrations/  <- 注释掉或删除这行

# 只忽略数据库文件
*.db
*.db-journal
*.db-shm
*.db-wal
```

### 2. 规范数据库路径配置

**统一使用相对于模块的路径**：

```env
# apps/backend/.env
DATABASE_URL="file:./prisma/data/portfolio.db"
```

**不要使用**：
- ❌ `file:./data/portfolio.db` - 相对于 CWD，不稳定
- ❌ `file:D:/absolute/path/portfolio.db` - 绝对路径，不可移植

### 3. 在 Git 提交前自检

创建 pre-commit hook：

```bash
# .husky/pre-commit
#!/bin/sh

# 检查 Prisma Client 是否最新
if ! npx prisma validate; then
  echo "❌ Prisma schema 有问题，请修复后再提交"
  exit 1
fi

# 检查构建是否成功
if ! npm run build -w backend; then
  echo "❌ 后端构建失败，请修复后再提交"
  exit 1
fi

echo "✅ 提交前检查通过"
```

在 README.md 中添加：

### 5. 定期备份数据库

```bash
# 创建备份脚本 scripts/backup-db.sh
#!/bin/bash

TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BACKUP_DIR="apps/backend/prisma/backups"
DB_FILE="apps/backend/prisma/data/portfolio.db"

mkdir -p "$BACKUP_DIR"
cp "$DB_FILE" "$BACKUP_DIR/portfolio_${TIMESTAMP}.db"

echo "✅ 数据库已备份到 $BACKUP_DIR/portfolio_${TIMESTAMP}.db"

# 只保留最近 10 个备份
ls -t "$BACKUP_DIR"/*.db | tail -n +11 | xargs rm -f
```

**在 package.json 中添加**：

```json
{
  "scripts": {
    "db:backup": "bash scripts/backup-db.sh"
  }
}
```

## 📚 技术原理说明

### Git 工作原理

Git 通过**快照**（snapshot）而不是差异（diff）来存储版本：

```
Commit A (snapshot)    Commit B (snapshot)    Commit C (snapshot)
├── src/app.ts (v1)    ├── src/app.ts (v2)    ├── src/app.ts (v3)
├── schema.prisma (v1) ├── schema.prisma (v2) ├── schema.prisma (v2)
└── package.json (v1)  └── package.json (v2)  └── package.json (v3)
```

当你执行 `git reset --hard <Commit A>` 时：
- Git 将工作目录中的**被跟踪文件**恢复到 Commit A 的快照
- **不会触碰**未跟踪文件（如 node_modules, dist, .env, *.db）

### Prisma 工作原理

Prisma 分为两个部分：

1. **Schema 文件**（`schema.prisma`）：
   - 定义数据模型
   - Git 跟踪，可回退

2. **Prisma Client**（`node_modules/.prisma/client/`）：
   - 根据 Schema 生成的 TypeScript 代码
   - Git 不跟踪，需要手动重新生成

3. **数据库文件**（`portfolio.db`）：
   - 实际存储数据的 SQLite 文件
   - Git 不跟踪，回退后可能与 Schema 不匹配

**不匹配示例**：

```
Git 回退前：
  schema.prisma (v2) → prisma generate → Prisma Client (v2) → portfolio.db (v2)
  ✅ 三者匹配

Git 回退后：
  schema.prisma (v1) ← Git 恢复
  Prisma Client (v2) ← 未变化
  portfolio.db (v2)  ← 未变化
  ❌ 不匹配！需要重新生成 Client 和同步数据库
```

### 为什么需要手动恢复

因为 Git **只管理源代码**，不管理**派生产物**：

| 类型 | Git 管理 | 原因 |
|------|---------|------|
| 源代码（.ts） | ✅ | 这是"源"，需要版本控制 |
| 编译产物（.js） | ❌ | 可以从源代码重新生成 |
| 依赖包 | ❌ | 可以从 package.json 重新安装 |
| 生成代码（Prisma Client） | ❌ | 可以从 schema.prisma 重新生成 |
| 数据库文件 | ❌ | 太大，变化频繁，不适合版本控制 |

**恢复流程本质**：
1. Git 恢复"源"（源代码、配置定义）
2. 手动重建"派生"（依赖、生成代码、构建产物）
